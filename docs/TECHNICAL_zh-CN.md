# SkyZH — 技术文档

> **这是面向开发者的技术文档。** 它描述翻译引擎的内部实现——渲染面、Mixin、语料格式，
> 以及用于换行和居中的像素测量。如果你是玩家，想了解这个 Mod 有什么用、怎么安装，
> 请看[主 README](../README.md)。

[中文](TECHNICAL_zh-CN.md) · [English technical documentation](TECHNICAL.md)

Hypixel SkyBlock 中文翻译 Mod。Minecraft 26.1.x 与 26.2 / Fabric，仅客户端——一套源码，
每个 Minecraft 一个 jar，见[构建](#构建)。

SkyBlock 没有官方中文，中文玩家要么花时间啃英文，要么截图分享给朋友时对方看一眼就划走。这个 Mod
把游戏里的文本换成中文，目标是让没玩过的人也愿意读下去，让新手不用先学词汇才能上手。

## 不会影响其他 Mod

翻译**只发生在文字被画到屏幕上的那一刻**，游戏状态一个字节都不改：

| 其他 Mod 读到的 | 状态 |
|---|---|
| `ItemStack` 的名称与 Lore 组件 | 英文原文 |
| 聊天历史 `allMessages` / 复制到剪贴板的内容 | 英文原文 |
| `Screen#getTitle()` 容器标题 | 英文原文 |
| `BossEvent#getName()` | 英文原文 |
| `Hud` 的 `overlayMessageString` / `title` / `subtitle` | 英文原文 |
| `Objective#getDisplayName()` 与 `Scoreboard` 里的计分板条目 | 英文原文 |

所有解析聊天的 Mod 都工作在网络包处理或 Fabric 的聊天事件上，那都在本 Mod 的注入点**之前**，
所以 SkyHanni、SkyBlocker 看到的永远是 Hypixel 原样发来的英文。这不是附带效果，是设计目标：
一个让 SkyHanni 失效的翻译 Mod，对绝大多数 SkyBlock 玩家来说比读英文更糟。

所有注入点都是 `require = 0`。万一某个版本的 Minecraft 改了方法、或者别的 Mod 抢占了同一条指令，
结果是"这部分不翻译了"，而不是"整个整合包启动崩溃"。启动日志里会打印各类目实际加载了多少条记录，
用来区分"还没翻译"和"没在工作"。

只有一条可选路径会去读网络包，而且要手动打开一个默认关闭的开关：下面「[运行时采集](#运行时采集默认关闭)」
那个补语料用的功能。它不改包、不改游戏状态、不改屏幕上任何一个像素。
它确实会往外发一样东西，而且只在这个开关打开时发：订阅 Hypixel 自己的位置事件，
见下面「[唯一一处会往外发的东西](#唯一一处会往外发的东西)」。

## 三个已知问题是怎么解决的

**居中错位.** Hypixel 用空格把文本凑成居中，空格数是按英文像素宽算的，换成中文就右边空一大截。
本 Mod 直接丢掉原有空格重算：容器标题、BossBar、动作栏、标题/副标题这几处 Mod 自己决定绘制坐标，
按译文真实像素宽重算，**精确到像素**；聊天横幅只能靠空格填充（一个空格 4px，误差约 ±2px），
但那也正是 Hypixel 自己那套居中术在英文下的精度，没有比原版更差。

**Lore 排版参差.** 保持和英文原版一样的左对齐（这是明确选择，不是没做）。真正要处理的是另一件事：
英文因排版被拆成两行的整句，在语料里合并成一条完整逻辑句翻译，渲染时把作为"尾巴"的那一行删掉，
并按客户端字体像素宽对合并后的中文重新折行（中文断行不看空格，CJK 字符间几乎处处可断，
但不会把句号、右括号之类甩到行首）。首行若尚未翻译，尾行原样保留——半句中文接半句英文是最糟的结果。

**颜色失真/丢失.** 一行 SkyBlock 文本经常中途换好几次色，切换点和句子结构对不上。语料用 `segments`
数组按颜色把原文分段，每段带自己的译文；渲染时**从屏幕上的实时文本读每一段的真实颜色**，
而不是信任语料里记的颜色码——记录是快照，Hypixel 一次更新就可能过时，而正在渲染的那行永远不会。
占位符捕获到的内容（玩家名、物品名、数值）连同它自己的颜色原样搬过去。若某条记录在实际游戏里
有多段颜色但语料只记了一整行，日志会点名该条记录提醒补 `segments`，同时仍按第一段颜色渲染。

### 动作栏是一排部件，不是一句话

SkyBlock 的动作栏中间那一行其实是它自己的 HUD：血量、所在地、法力、防御、以及临时顶上来的经验
提示，五个空格隔一格并排画在一起——

```
2,610/2,235❤     ⏣ 升降梯     469/469✎ 400⸕     104/104♨
```

整行去查表永远查不到，因为里面每个数字都随玩家走动在变，两帧之间就是两句不同的"话"。所以渲染前
先按**宽间隔(≥3 个空格)**把它切成部件，每个部件各查各的表，中间的空格原样放回去——那是 SkyBlock
自己量好的排版，中文部件仍旧落在英文部件的位置上。整行**先**试一次:哪条记录把整行写出来了，
那条说了算，所以服务器居中过的单条动作栏消息不受影响。

同一套切法也用在采集上。切之前一次会话采到八百多条只有数字不同的整行记录，切之后是十几个短部件，
其中一半是"数字加一个图标"、压根没有词，采集器自己就不收了。

### 计分板与"闪动"

侧边栏是全游戏唯一真会逐帧变化的表面：Hypixel 每 tick 重发一次 objective 的显示名，纯文本恒为
`SKYBLOCK`，变的是逐字符颜色——一道高光在字母间扫过，这就是那个闪动效果。两处配合才能保住它：

- **不缓存渲染结果**。本 Mod 只缓存"哪条记录匹配这段文本"，文本逐帧不变所以命中是对的；
  上色每帧重做，动画自然保留。
- **逐字符摊分颜色**。8 个字母变 4 个汉字，若统一取首字母的颜色，扫动会退化成整词闪烁。
  所以每个汉字从它所代表的那段字母里取色；又因为一个汉字盖两个字母、一格宽的高光会有一半帧落空，
  取色时优先取该段里**不同于全词主色**的那个，于是高光不会被丢掉，只是每个位置停留两帧。

注入点也特意选在**读取文本**处而不是绘制处：`displayScoreboardSidebar` 要先量标题和每一行的宽度，
才能决定面板多宽、左边界在哪、标题居中从哪开始。在源头翻译，这些测量量的就是中文；
在绘制处翻译，面板会按英文尺寸裁好、中文塞在里面对不上。

## 设置

Mod Menu 是软依赖。没装也能用，改 `config/skyzh.json` 即可，文件里带中文说明。

| 选项 | 默认 | 说明 |
|---|---|---|
| `enabled` | 开 | 总开关。关闭后不翻译任何文本 |
| `translateSkyBlockName` | 开 | 把 SkyBlock 译作「空岛生存」。复合词里自动用简称并修正空格：`你的 SkyBlock 等级` → `你的空岛等级`，`+150 SkyBlock XP` → `+150 空岛经验`；独立出现仍用全称。尚未翻译的英文句子里也生效，但**有条件**，见下面「在哪替换、在哪不替换」 |
| `showOriginal` | 开 | 中文旁边保留英文原名，如「收藏品（Collections）」。**容器标题和物品名**都生效——集市、拍卖行是按英文名搜索的，只留中文等于把搜索关键词一起翻掉了。标题区放不下时英文截断，物品悬浮框会自己变宽 |
| `captureUntranslated` | **关** | 给补语料的人用的开发者开关，会往硬盘写文件，普通游玩请保持关闭。见下面「运行时采集」 |

### 在哪替换、在哪不替换

这个词会出现在没人翻过的英文句子里，所以它恰好是全 Mod 唯一一处可能造出"本 Mod 存在就是为了消灭的那种东西"
的地方：一整行英文里孤零零一个中文词。因此在语料**没有**覆盖的行上，只有当 `SkyBlock` 是这一行里
唯一的英文词时才替换（判据见 `SkyBlockName.isTheOnlyEnglishWord`，数字和符号不算英文词）。

| 行 | 结果 |
|---|---|
| `SKYBLOCK`（侧边栏标题） | 空岛生存 |
| `SkyBlock Level 42` | 不动——`Level` 还是英文 |
| `You unlocked SkyBlock XP!` | 不动 |
| `SKYBLOCK CO-OP` | 不动——见 `TODO.md` |

语料**已经**覆盖的行上，替换是在译文之上跑的，所以一条译文里保留了这个词的记录——`"SkyBlock 菜单"`——
开关打开时显示「空岛菜单」，关闭时显示 `SkyBlock 菜单`。想让某一行早点翻出来，正规做法就是这个：
写记录、译文里把词留着，开关照旧管得住它。

### 玩法名的空格与简称

译文里把 `SkyBlock` 前后留空格是正确的中文排版（拉丁词与汉字之间该有空隙），但换成中文之后这些空格
就成了汉字之间的空格，中文里并不存在，会显示成「你的 空岛生存 等级」这种断开的样子。所以替换时会重新
判断：空格两侧都变成汉字就删掉，一侧仍是数字或字母就保留（`+150 空岛经验` 里那个空格是对的）。

同时按中文习惯在复合词里用简称：后面紧跟汉字说明构成了「空岛菜单」这类偏正结构，用「空岛」；
独立出现（后面是标点、字母、行尾）用全称「空岛生存」。少数助词方位词不算复合，
`在 SkyBlock 中` 仍是「在空岛生存中」。译名、简称和这张排除表都在
`_shared/SkyBlock_Name.json`，改文件即可，不用动代码；把 `short` 设成和 `full` 一样就等于关掉简称。

### 属性图标是服务器字体画的

SkyBlock 以前把属性图标当普通字符发（`❤ Health`、`☘ Mining Fortune`、`⸕` 是 Amber），现在改成了
私用区码点，由服务器资源包里的字体渲染。语料的两个来源对这件事的说法不一致：wiki 记的是老符号，
NEU-REPO 里是抓取当天服务器发的那种。

写法不同的两边永远匹配不上，而且**什么征兆都没有**——不报错、数据也不算坏，就是那句话一直是英文。
所以匹配前会把两边折算成同一种写法，画中文时再把图标换回**服务器这一行实际发的那个字符**：
屏幕上的图标还是 SkyBlock 自己的，只有字变成了中文。

### 藏在词中间的标记

计分板的每一行必须是互不相同的字符串，Hypixel 的办法是往文字里塞一个 `§` 加一个字母——
`Dwarven M§qines`、`W§qind Compass`——每一行塞的位置还不一样。`q` 不是任何一种颜色，
而这正是重点：游戏的渲染器碰到 `§` 就把它和后面那个字符整对吃掉，认不认得都一样，
于是这个标记在数据里存在、在屏幕上不存在。

Minecraft 自带的 `ChatFormatting.stripFormatting` **不是**这么做的——它只删有名字的颜色码，
剩下的原样留着——用它读文本的 Mod，读到的就是两个玩家看不见的字符。
这点差别值得单写一段，是因为它坏掉的东西有多少：计分板那几行永远匹配不上记录、一直是英文，
采集下来的每一行都被归到一个叫 `Dwarven M§qines` 的地方去。
现在本 Mod 里所有把文本摊平的地方都走同一个读法 `StyledText.plainOf`，也就是渲染器的读法。

## 翻译语料

语料在 `original_text/`，按玩法分类 × 渲染位置分目录，规范见 `original_text/README.md`。
Mod 直接读取这些文件本身（原样打进 jar），没有中间生成格式——屏幕上一行不对，就能直接查到是哪个文件的
哪个 `id`。`zh` 为空表示尚未翻译，该行保持英文，不会被抹掉。

改完语料跑一次回归测试，不用进游戏：

```bash
./gradlew checkTranslations
```

它用真实语料跑真实匹配引擎，逐条核对颜色重建、占位符搬运、缩进保留、类目隔离等结果。
唯一覆盖不到的是需要字体的部分（折行与居中要量像素），那些只能在游戏内验证。

另一半问题不是「这条记录对不对」，而是「实际玩一局，屏幕上出现过哪些语料压根没收录的句子」。
把同一个引擎对着客户端日志跑一遍就有答案：

```bash
./gradlew auditLog                        # 读 logs/ 下所有日志
./gradlew auditLog -Plog=logs/latest.log  # 只读一个
```

Minecraft 本来就会把收到的每条聊天消息写进 `logs/`，这个任务只是读那个已经存在的文件。
输出是「没有任何记录应答的行」，按出现次数排序。

## 运行时采集（默认关闭）

日志只有聊天。**NPC 打开的那个界面里每一格物品叫什么、Lore 写了什么**，日志里没有，wiki 的
`/UI` 子页覆盖不全，NEU-REPO 只有物品本体不含菜单——这块内容只存在于「有人正在玩的那块屏幕上」。
`captureUntranslated` 就是为这一块存在的：打开之后，语料答不上来的服务器原文会被写到
游戏目录下的 `skyzh-capture/`。**它不改变游戏里显示的任何东西**，只读不写。

### 为什么这次不会把别的 Mod 的文字采进去

上一次做这个功能就是栽在这里，而且没法补救：文本一旦画到屏幕上就只是文本，SkyHanni 画的那一行
和服务器发的那一行长得一模一样，事后再怎么过滤都分不出来。**错的是挂钩子的位置，不是过滤规则。**

这次每一个采集点都挂在**数据包处理函数**上，或者挂在只有数据包才写得进去的状态上：

| 采什么 | 挂在哪 | 为什么进不来别的 Mod 的东西 |
|---|---|---|
| 聊天（系统 / NPC） | `ClientPacketListener#handleSystemChat` HEAD | 比 Fabric 的聊天事件、比 SkyHanni / SkyBlocker 都早。Mod 自己发的消息走 `ChatComponent#addMessage`，**根本不经过这个方法** |
| 界面标题 | `handleOpenScreen` HEAD | 服务器包里的 `title` 字段 |
| 物品名 + Lore | `handleContainerContent` / `handleContainerSetSlot` HEAD | 读 `ItemStack` 的 `CUSTOM_NAME` / `LORE` 组件，**不是** `getTooltipLines()`——后者正是所有 Mod 往 Lore 里加东西的地方 |
| 计分板 | 每 10 tick 读一次 `Scoreboard` 对象 | 和原版渲染读的是同一份服务器状态。附带好处：**SkyHanni 的自定义计分板把侧边栏整个接管之后，这里照样拿得到 Hypixel 的原始行** |
| Tab 列表 | `handleTabListCustomisation`（页眉页脚）+ 每 10 tick 读一次玩家条目 | 同上 |
| BossBar | `BossHealthOverlay#update` TAIL | 那张 map 只有服务器包写得进去 |
| 动作栏 / 标题副标题 | `setActionBarText` / `setTitleText` / `setSubtitleText` HEAD | 同上 |

注意这里**故意没有**按名字过滤：`[Bazaar]`、`[Sacks]` 是 Hypixel 自己的前缀，做一张「Mod 名黑名单」
只会把真的 SkyBlock 文本误杀掉，去挡一个本来就进不来的东西。

再加两道闸：服务器地址要匹配 `captureServer`（默认 `hypixel.net`，留空则不检查），
且侧边栏标题必须是 SKYBLOCK。两个条件都不满足时一行都不采。

### 唯一一处会往外发的东西

采集**打开**时，而且只有装了 [`hypixel-mod-api`][modapi] 这个 Mod 时，SkyZH 会订阅 Hypixel
自己的位置事件——一个注册包，由那个 Mod 的管道发出去，内容就是"我要这个事件"。
换来的是玩家一落地服务器就直接告诉你人在哪个岛，也就是把"这段文本该归哪个玩法"这件事
从"读一块画给人看的侧边栏"换成"问服务器"。那个库只在编译期引用、不打进 jar；
没装那个 Mod 这段代码根本不加载，另外两个读法照旧。

采集**关闭**时——也就是所有普通玩家——什么都不订阅，什么都不发。
翻译那一半仍然是标题上写的那句话：装了 SkyZH 的客户端，在 Hypixel 和别的 Mod 眼里，
就是一个跑英文的客户端。

[modapi]: https://github.com/HypixelDev/ModAPI

### 采到的东西长什么样

输出分三堆，各自再按 `original_text/` 的结构分目录（玩法 / 渲染面 / 名字）：

```
skyzh-capture/
├── untranslated/          没有任何记录应答的行
│   ├── Mining/NPC_Message/Fragilis.json
│   ├── Mining/GUI_Item/Commissions.json        ← 这个菜单里所有格子的名字 + Lore
│   └── _Unknown_Gameplay/ScoreBoard/Sidebar.json
├── mixed/                 有记录应答了，但屏幕上仍然中英混杂
│   └── Mining/ChatMessage/Server_Messages.json
└── colour/                有记录应答了、每个字都是中文，颜色却被压平了
    └── Mining/ScoreBoard/Sidebar.json
```

第三堆是别的办法很难发现的那一类。游戏里一行文字中途换色，语料里却记成了一整行，
译文就会被整段刷成最前面那个颜色——金色的 `5` 旁边一个白色的 `(+`，蓝色的数值旁边一个白色的雪花。
启动日志只能说「这条记录压平了颜色」，永远说不出**颜色是在哪儿换的**；采集文件说得出来，
它会按服务器实际发的颜色边界把 `segments` 数组切好写进去，指名道姓地告诉你抄进哪条记录。

这里只认**画得出来**的那部分样式。Hypixel 会为了挂一个悬浮提示而把一行切开，切法和换颜色时一样——
收纳袋那条消息里 `" items"` 和后面的 `"."` 是同一种黄色的两段，区别只在前一段带着「Added items:」的悬浮框——
按整个 `Style` 相等去判断，就会把一条 `segments` 本来就正确的记录推进这一堆，
还建议你在一个两边颜色相同的位置再切一刀。所以比较只看颜色、字体和五个格式开关。

玩法从"采集当时人在哪"推断，对照表在 `assets/skyzh/capture/areas.json`，
认不出来就落进 `_Unknown_Gameplay`，补一条到那个文件即可，不用改代码。

"人在哪"有三个读法，按这个顺序问：侧边栏 `⏣` 那一行 → Hypixel Mod API（装了 `hypixel-mod-api` 才有）
→ Tab 列表的 `Area:` 那一行。顺序不是随手定的——侧边栏给的是岛上的小地名
（Fairy Grotto 而不是 Crystal Hollows），最细，但它是由队伍的前缀和后缀拼出来的，
每次传送之后也是最后才拼好的一块，而那正好是另外两个读法已经能答话的时候。
在两个读法都还没答话的那一两秒里采到的文本会被**扣住**，最多等八秒，
等地点出来了再按那个地点落盘——那本来就是它来自的地点。
只有侧边栏自始至终不答话，才会有东西真的落进 `_Unknown_Gameplay`；
真到那一步，日志里会把侧边栏和 Tab 列表原样打出来（看不见的字符写成 `\uXXXX`），
否则"一堆未知玩法"和"表里少一条"从输出上根本分不出来。
来源认不出来落 `_Unknown_Surface`，名字认不出来落 `_Unknown_Name`。

每条记录就是 `original_text/` 的记录格式，颜色码原样保留、变色的行自动切好 `segments`、
`zh` 留空。搬进语料只需要删掉 `_capture` 块、核对占位符、填 `zh`。

### 采到东西会在聊天里说一声

打开采集就自带，没有额外开关。采集到的会**按输出文件合并**，最后一条进来 1 秒后发一条：

```
§b[SkyZH]§f 采集 43 条 · §7Mining / GUI_Item / §eCommissions§8  在 Dwarven Mines
         §7未翻译 41、中英混杂 2  §9[打开未翻译]  §9[打开中英混杂]
```

末尾那个"在 XXX"是采集当时侧边栏报的**地点**,只有它和玩法目录不是一回事时才写。
`Hub_General` 是个目录不是个地方——大厅、私人岛屿、博物馆的通用文本都落在那里,
只报目录名的话,在自己岛上开的菜单看起来就像是在大厅开的。

为什么要合并:一个 SkyBlock 菜单服务器一口气发 54 格物品、每格十几行 Lore,逐条发会瞬间刷四十行,
把聊天框(默认只显示 10 行)里别的东西全顶掉。聊天类文本本来就是一条一条进来的,
合并对它没有影响——一条消息安静下来的那一刻就发了。文件名可以点,用系统默认程序打开那个 JSON,
鼠标悬停能看到完整路径。持续采集超过 5 秒也会强制发一条,不会一直攒着。

这条消息是**客户端消息**(`addClientSystemMessage`),不是伪装成服务器发的。它不经过数据包,
所以采集器看不见自己;但 Minecraft 会把它写进 `logs/latest.log`,所以 `auditLog` 那边按
`[SkyZH]` 前缀跳过了它,不会把自己的提示当成未翻译文本报出来。

### 它替你判断的几件事

**同一句话只有数字/名字不同的，会归并成一个模板。** 这是上次搁置的第二条理由（分不清哪部分是
可变数值），答案是：一次观测确实分不出来，多次可以。**只有同一位置被观察到 ≥2 种取值才敢当成占位符**，
而且见过的取值全部列在 `_capture.observed` 里给人复核；只见过一种取值的位置原样留着不猜。
切口还不许落在数字中间（`x23`/`x24` 的模板是 `x%s` 而不是 `x2%s`），也不许落在单词中间
（`Force`/`Axe` 不会被切成 `Forc`/`Ax`）；占位符比句子本身的词还多时直接拒绝归并，
免得把「你 XX 了 YY」这种语法当成一句话。

**同一行在别的菜单里出现过就不再记一份。** SkyBlock 每个菜单都带着同一套返回按钮、同一段稀有度
说明，指南类菜单每一页顶上还是同一段介绍；而且**容器内容包尾部那 36 格是玩家自己的背包**，
每开一个菜单都跟着发一遍。按菜单各记一份的结果是：一次会话 9758 条记录里，有 5208 条是隔壁文件
里那条记录的副本。现在背包那 36 格落进 `_Inventory`，跨菜单重复的行只留第一次见到的那一份，
其余出现过的菜单记在 `_capture.also_seen` 里——那一行有 `also_seen`，就正好说明它该按 §5.6
抽进 `_shared/`。同一玩法内才去重，把 Foraging 的行记进 Mining 的文件夹是没人事后能发现的污染。

**别人的名字进不来。** Hypixel 在等级和称号之间画一个公会图标(`⸕`、`ᛝ`——有些还是字母)，
名字后面再挂 AFK / 组队符号。以前这几个符号让"这一行只是个玩家名"的判断失效，
于是一次会话把三条陌生人的聊天和五十个陌生人的用户名写进了采集文件。

**已经是中文的行不采。** Hypixel 自己有一部分中文文案（大厅传送、进服公告），那不是本 Mod 的活。

**「差一点就匹配上」会被指名道姓。** 一行没被翻译，但语料里**确实有**这句话、只差在不可见字符上
（私用区图标、不间断空格、全角标点）——这是本项目最贵的一类 bug，因为看屏幕、看日志、看数据文件
都看不出来。现在这种情况会在记录里写一条 `near_miss`，指出是哪个文件的哪条记录，
并把两边的文本都用 `\uXXXX` 转义打出来。

### 自检

```bash
./gradlew checkCapture
```

拿真实会话里的文本跑整条采集链路：颜色还原、模板归并、说话人识别、两堆的分类、落盘目录结构。

### 把采集结果倒回去看

照着采集结果补完记录之后，下一个问题是「补对了没有」。采集文件里逐字保留了原文，
连颜色码和图标字形都在，所以直接拿它回放就行：

```bash
./gradlew replayCapture                    # 回放 logs/skyzh-capture 全部
./gradlew replayCapture -Pcapture=<目录>   # 只回放某个玩法 / 渲染面 / 单个文件
```

每一行都会连「现在渲染成什么样」一起打出来。这一步能抓到 `checkTranslations` 结构上抓不到的问题：
那个检查只知道语料对自己的说法，所以分段顺序写反了、手写的空格夹在两个汉字中间、
某个值忘了加进 `_shared/Terms.json`——这些都能通过检查，屏幕上却还是不对。在这里是一行输出的事。

## 构建

```bash
./gradlew dist     # 两个 jar 都产出到 build/dist，产出前两个版本的检查都会跑一遍
./gradlew build    # 同样两个 jar，各自留在自己的 build/libs 里
```

需要 JDK 25。Minecraft 26.x 不再混淆，因此没有映射层，Mod 之间是普通依赖关系，
Loom 也不再有 `remapJar` 这一步——`jar` 出来的就是能装的那个文件。

### 两个 Minecraft 版本，一套源码

| | jar | 声明的 Minecraft | 编译时用的 Mod Menu |
|---|---|---|---|
| `fabric-26.1/` | `SkyBlockZH-<版本>-Beta-26.1.jar` | `>=26.1 <26.2` | 18.0.0 |
| `fabric-26.2/` | `SkyBlockZH-<版本>-Beta-26.2.jar` | `>=26.2 <26.3` | 20.0.1 |

两个目标都编译 `src/main/`——引擎、语料加载、采集，以及十二个 Mixin 里的九个——
再各自加上一小棵自己的树：`src/mc26_1/` 或 `src/mc26_2/`。除了版本号本身，
一个目标的其他部分全部写在 `gradle/target.gradle` 里，所以两边不可能在"语料怎么打包"
或"编译到哪个 Java 版本"上悄悄走岔。

两个 Minecraft 之间只有四处不同，每一处都是版本树里的一个文件：

| 动了什么 | 26.1.x | 26.2 |
|---|---|---|
| 画 HUD 的类 | `Gui` | 从 `Gui` 里拆出来的 `Hud` |
| 玩家实体类型常量 | `EntityType.PLAYER` | `EntityTypes.PLAYER` |
| `SubmitNodeCollector#submitNameTag` | 末尾多一个 `double` | 没有 |
| 谁持有聊天框和屏幕栈 | `Gui#getChat`、`Minecraft#setScreen` | `Gui.hud#getChat`、`Gui#setScreen` |

最后一行是 `platform/ClientGui`，每个目标一份，方法签名相同。前三行是 `mixin/HudMixin`、
`mixin/HudScoreboardMixin` 和 `mixin/EntityRendererMixin`——**只有注解**；
它们被触发之后做什么，是 `hook/` 里的共享代码，只写一遍。

一个 jar 覆盖 26.1、26.1.1、26.1.2 全部三个版本：这个 Mod 碰到的每一个类，
在三个版本里的字节码完全一致。两个版本范围的上界都是故意封死的。
把 jar 装到不是为它编译的那个 Minecraft 上并不会崩——因为这里每个注入点都是 `require = 0`，
结果会是 HUD、侧边栏和所有头顶浮空字**悄无声息地全是英文**——
所以那个上界的作用，是让 Fabric 根本不去加载它。

### 怎么确认注入点还在

```bash
./gradlew checkMixinTargets     # 是 `check` 的一部分，两个目标都会跑
```

这是 `require = 0` 让人不得不做的检查。它把**编译产物**里的注解读回来——真正的 `@Mixin` 值、
真正的 `method` 列表、真正的 `At.target`——然后逐个去那个目标编译时用的 Minecraft 里查，
`@Shadow` 成员也查：那些不是 `require = 0`，对不上是在应用 Mixin 时直接崩，而不是安静地失效。
能编译只能证明这个 Mod 的源码自己跟自己一致，完全不能证明注入点还在。
见 `gradle/check_mixin_targets.py`。

想拿现有产物去对一个当前没在编译的 Minecraft——`>=26.1 <26.2` 这个范围就是这么定下来的，
不是猜的：

```bash
./gradlew :fabric-26.1:build -Pmc26_1_version=26.1.2   # 用后面的补丁版本重新编译 26.1 这棵树
```
