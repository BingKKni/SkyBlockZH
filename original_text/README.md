# original_text 数据规范

本目录存放从 Hypixel SkyBlock 采集来的**原文(英文)**文本,按玩法与文本类型分类。
**本阶段只采集原文,不做翻译**——每条记录预留 `zh` 字段留空,翻译工作在后续阶段进行。

## 1. 目录结构

```
original_text/
  README.md            本文件
  GLOSSARY.md           一词多义 / 需要统一译名的术语表
  SOURCES.md            数据来源说明与可信度排序
  <玩法分类>/            Mining, Farming, Foraging, Fishing, Combat,
                         Dungeons, Rift, Taming, Events, Economy, Hub_General
    NPC_Message/         按 NPC 名字建文件,如 King.json
    GUI_Title/           箱子/菜单界面标题,按菜单名建文件
    GUI_Item/            物品名称 + Lore,按物品或物品组建文件
    ScoreBoard/          计分板(侧边栏)文本
    TabList/             Tab 列表(按 Tab 键弹出的玩家列表侧栏)文本,和 ScoreBoard 是不同的渲染面,
                         不要混在一起(2026-08-18 从 ScoreBoard 拆出;2026-08-19 代码侧已补齐
                         Surface.TABLIST 与 PlayerTabOverlayMixin,本目录内容现在会真正渲染)
    Hologram/            NPC 头顶的浮空文字(实体名字,画在世界里而不是 HUD 上)。同一个词在这里
                         和在聊天里意思可能不同——头顶的 CLICK 是操作提示,聊天里的 CLICK 是句子
                         的一部分,所以自成一个渲染面。**这个面没有运行时采集**,每条都要进游戏
                         照屏幕抄,见该目录下文件的 todo
    BossBar/             BossBar 文本
    ActionBar/           动作栏提示(屏幕下方短暂提示,SkyBlock 大量使用)
    ChatMessage/         系统/广播聊天消息(非 NPC 对话,如升级提示、拾取提示)
    Misc/                标题画面(title/subtitle)、其他不属于以上分类的文本
```

玩法分类的选择依据 SkyBlock 的技能/玩法体系,而非 Wiki 的页面结构,
一个 NPC/GUI 如果横跨多个玩法(例如集市 Bazaar 既属于 Economy 也可能被别的玩法引用),
按其**主要出现场景**归类,并在 `source` 字段注明,不必严格互斥。

## 2. 通用字段

每个 JSON 文件顶层建议包含:

```json
{
  "source": "https://hypixelskyblock.minecraft.wiki/w/XXX",
  "fetched_at": "2026-08-18",
  "verified_ingame": false,
  "...": "该文件类型特有字段,见下"
}
```

- `source`: 采集来源 URL,方便日后核实。
- `fetched_at`: 采集日期(YYYY-MM-DD),Wiki 内容会随游戏更新变化。
- `verified_ingame`: 是否已经在游戏内截图/实测核对过文本(Wiki 文本,尤其是
  ScoreBoard / ActionBar / BossBar,常年缺失或过时,标记为 `false` 提醒后续核实)。

## 3. 每条文本记录的字段

```json
{
  "id": "king_today_is",
  "context": "告知今天在位的国王是谁",
  "text": "Today the King is %s.",
  "placeholders": [
    { "token": "%s", "desc": "当前在位国王的名字(专有名词,不翻译)", "type": "npc_name", "example": "Brammor" }
  ],
  "gloss": "",
  "translate": true,
  "zh": ""
}
```

- `id`: 全文件内唯一、稳定的字符串 ID,给代码引用用(蛇形命名)。**不要用行号**,
  因为 Wiki 内容增删会导致行号漂移;`id` 一旦定下尽量不改,方便以后追踪翻译状态。
- `context`: 简短中文说明这句话什么时候出现、谁说的、在什么流程里——**给译者看**,
  不是给玩家看的正式文案。
- `text`: 原文,英文,一字不差摘自游戏/Wiki。含变量部分用占位符(见第 4 节)。
- `placeholders`: 占位符说明数组,没有占位符则为空数组 `[]`。
- `gloss`: 可选。当这句话里有一词多义或容易误译的词时,写清楚这里的英文原意是什么、
  不应该翻成什么。没有歧义就留空字符串。
- `translate`: 是否需要翻译。默认 `true`。像 NPC 名字本身、物品 ID 名等专有名词条目设为
  `false`,但仍然采集下来,因为翻译系统需要知道"这个词出现在这里,决定不翻译"。
- `zh`: 译文,本阶段留空字符串 `""`,占位。**不要删除这个字段**,后续阶段直接填。
- `raw`(可选): 带 Minecraft 颜色/格式代码(`§7`、`§l` 等)的**原样**文本,来自
  NotEnoughUpdates-REPO / SkyHanni 等能拿到精确字节的来源时才填。`text` 字段永远是
  去掉颜色码之后的干净文本,给译者读;`raw` 是给代码做正则匹配/保留颜色分布用的。
  只能从 Wiki 摘要拿到文本时,没有 `raw` 也没关系,留空或不写这个字段,
  但要在文件顶层 `verified_ingame` 保持 `false` 提醒后续用精确来源核对。

### 颜色片段 `segments`(处理行内多次变色)

同一行原文经常在句子中途切换颜色(如 `"§7Damage: §c+%s"`),且切换点不一定对着
占位符(如 `"§7Grants §2+%s%% Mithril Powder§7."` 里 "Mithril Powder" 前后的颜色边界
和占位符对不上)。**只存一个整行 `zh` 无法还原这种行内变色**——中英文词序、断句方式
不同,翻完之后没法靠对齐算法猜出中文哪几个字对应原来哪段颜色。

处理规则:检查 `raw` 字段,如果一行原文出现了 **多次**(≥2 处)颜色/格式代码切换,
在该条记录里加一个 `segments` 数组,按颜色分段,每段自己带独立的 `zh`:

```json
{
  "id": "xxx",
  "raw": "§7Damage: §c+%s",
  "text": "Damage: +%s",
  "segments": [
    { "color": "§7", "text": "Damage: ", "zh": "" },
    { "color": "§c", "text": "+%s", "zh": "" }
  ],
  "zh": ""
}
```

`text`/顶层 `zh` 仍然保留(给不需要关心颜色细节的场景,如统计词频、机器翻译草稿用),
但**只要存在 `segments`,最终定稿翻译以 `segments[].zh` 为准**,顶层 `zh` 视为草稿/摘要。
只有一种颜色、行内没有切换的行(大多数情况)不需要 `segments`,继续用 flat `text`/`zh` 即可,
不要为了"规范统一"给每一行都套这个结构,增加不必要的臃肿。

### 属性图标写通用符号,不用管游戏里的私用区字形

SkyBlock 以前把属性图标当普通字符发(`❤ Health`、`☘ Mining Fortune`、`⸕` 是 Amber),
现在改成了**私用区码点**(`U+E010`、`U+E053`、`U+E015`),由服务器资源包里的字体渲染。
两种写法在采集源里同时存在:wiki 记的是老符号,NEU-REPO 里是抓取当天服务器发的那种,
游戏里发的是新的。

**采集/翻译时都写通用符号即可**(`❤`、`☘`、`⸕`、`▚`、`✧`、`❄`)。引擎在匹配前会把两边折算到
同一种写法(见 `text/Glyphs.java`),渲染时再把图标换回这一行**服务器实际发的那个字符**——
屏幕上的图标还是 SkyBlock 画的那个,只有字变成中文。

这条以前不知道,症状是"记录看着没问题,游戏里就是不翻译":一条写着 `❤ Health` 的记录
永远匹配不上画着 `U+E010` 的那一行,而且什么日志都不会打。

### 只有符号、没有单词的模板是允许的

`"%s: %s"` 这种"除占位符外只剩 ASCII 标点"的模板会匹配整个渲染面的每一行,引擎照旧拒绝。
但**符号算这一行自己的词**:计分板顶上的所在地行就是 `"⏣ %s"`,那个面上没有别的行以 ⏣ 开头,
这个符号和一个单词一样有辨识度,而且整行除了地名本来就没有别的内容。

### 占位符不会吞掉服务器凑居中的空格

聊天横幅是用前置空格凑居中的。`"%s STARTED!"` 这种模板曾经会把那串空格一起捕进 `%s`,
表面上照样能匹配,实际上两件事都坏了:捕获值变成 `"  GONE WITH THE WIND"`,查不到词表;
这一行也不再被认成"服务器居中过的行",译文的居中重算就不会发生。
现在捕获值两端不允许有空格(见 `text/Capture.java`),整行匹配失败之后引擎会自动改用
"剥掉空格再查"的那一次,空白原样回到 `head` 里。

### 居中 vs 缩进——按"文本所在位置"分类,不要靠代码检测单条字符串

同样是行首空格,有可能是"手动居中凑出来的"也可能是"表示层级的缩进",这两种**不可能
靠检测字符串本身分辨**(两者看起来完全一样)。正确做法是按**文本所在的 UI 位置分类**,
一次性定策略,而不是每条数据单独判断:

- **`GUI_Title/` 整个分类**:箱子/容器界面标题客户端不会自动居中,SkyBlock 服务器一直是
  针对一个**固定已知的目标宽度**(Minecraft 容器标题区的像素宽度是引擎常量)手动居中的。
  这个分类下**默认全部当作"要居中"**处理,不需要逐条判断,Opus 写代码时对这整个分类
  统一按目标宽度重新计算居中空白,原文里的空格数直接丢弃不用。
- **列表项 / 对话层级缩进**(比如 `Keeper_of_the_Crystal.json` 里的 `"  %s"`):这类缩进
  没有"要对齐的目标宽度",只是表示"这一行比上一行更靠右一点"的相对关系,**默认策略是
  照抄原文的空格数,或者干脆固定用一个小缩进,完全不需要测量宽度**。不用打任何标记。
- **聊天横幅/公告消息**(活动开始之类,两边常有对称装饰符号如 "✦ ✦ ✦"):这是**少数例外**,
  因为"两边对称装饰符号"这个视觉特征人工看一眼就能认出来,遇到时在该条记录加一个
  `"layout": "center_chat_banner"` 标记即可,让 Opus 的代码只对带这个标记的少数行做
  居中重算(针对 Hypixel/Minecraft 社区公开的"聊天框居中术"假设的默认聊天框宽度,
  不是真的去读每个玩家的聊天框设置——这个技巧本身在英文原版下也只是"大多数情况下居中",
  不是像素级保证,中文版沿用同一套假设即可)。

采集阶段不需要给每条记录都打居中/缩进标记——**只有"聊天横幅公告"这一种少数例外需要
显式标记,其余两种(标题永远居中/缩进永远照抄)都是按分类的默认规则,不用逐条处理**。

### 关于换行与居中——采集阶段不用决定,但要理解为什么

英文原文里因为排版被拆成多行的"其实是一整句话"(比如钻头 Lore 里 "Increases fuel
capacity with part" + "installed." 硬拆成两行),**必须在数据里合并记成一条完整逻辑句**,
不要保留成两条各自独立、断头的记录——本文件前面 GUI_Item 的规则和 `_shared/Item_Boilerplate.json`
已经这么做。原因:中文翻译后的断行位置和英文原文的断行位置几乎不可能对齐(中文字符更宽,
换行必须由 Opus 在渲染时用客户端字体测量像素宽度动态重算,不能照抄英文行数),
如果数据里保留的是被砍断的英文半句,翻译者根本没法翻出正确的整句中文。
同理,菜单标题前用来"手动居中"的空格数、缩进空格数,这些**采集时原样记录 raw 即可,
不要在数据里尝试"翻译"这些空格本身**——居中效果是运行时按译文实际像素宽度重新计算的,
不是翻译文件要解决的问题。

### 跨行整句的标记 `continuation`

上一节说明了"英文里被拆成两行的其实是一整句"必须合并成一条完整逻辑句翻译。**代码需要一个
机器可读的标记才知道哪一行是"尾巴"**——`zh` 为空在本项目里一律表示"这条还没翻译，保持英文"，
不能同时又表示"这行被合并掉了，删掉它"，否则大批尚未翻译的条目会被整行抹掉。

因此约定:句子的**首行**照常填完整译文，**尾行**保持 `zh: ""` 并额外加 `"continuation": true`:

```json
{ "id": "drill_fuel_tank_desc_1", "text": "Increases fuel capacity with part",
  "translate": true, "zh": "增加已安装配件的燃料容量。" },
{ "id": "part_installed_suffix", "text": "installed.",
  "translate": true, "continuation": true, "zh": "" }
```

运行时行为:

- 首行**已翻译** → 尾行整行删除，首行的完整译文按客户端字体像素宽重新折行（中文通常更短，多数情况
  两行并作一行）。
- 首行**未翻译** → 尾行原样保留，两行都是英文。半句中文接半句英文是最糟的结果，宁可都不翻。

**不要**给"两半各自本来就是两句话"的情况打这个标记——`continuation` 只用于"英文因排版被迫断开、
中文不需要在同一位置断开"的那一种。判断依据是**英文原文**：首行的英文如果不以句末标点结尾、
尾行的英文以小写词开头，那它们就是同一句被拆开的，该用 `continuation`。

> ⚠️ 反过来最容易出的错：**把首行的 `zh` 改写成一句完整的话，却忘了同时把尾行改成 `continuation`。**
> 尾行还留着自己那半句的旧译文，屏幕上就把同一件事说两遍——比如
> "找「钻头技师」为这个钻头安装配件!" 底下又跟一句 "「钻头技师」聊聊吧!"。
> 这个错误已经在本项目发生过两次（钻头配件提示、嘉年华门票），所以改任何一条跨行整句的首行译文时，
> 顺手 `grep` 一下同文件里承接它的那条记录，确认尾行已经标成 `continuation`，避免同一句话在游戏里显示两遍。

### 颜色分段里的语序调整 `omit`

英文把中心词放前面、中文放后面,所以 "Long live the **Fallen Star**!!!!" 的中文是
"**陨落之星**万岁!!!!"——英文有三段颜色,但第一段("Long live the ")在中文里没有对应的字,
它的意思跑到后面那段里去了。

这种情况给那一段加 `"omit": true`:

```json
"segments": [
  { "color": "§f", "text": "Long live the ", "zh": "", "omit": true },
  { "color": "§d", "text": "Fallen Star",    "zh": "陨落之星" },
  { "color": "§f", "text": "!!!!",           "zh": "万岁!!!!" }
]
```

`omit` 和"`zh` 留空"是两回事,不要混用:

- `zh: ""` = **这段还没翻译**,渲染时保持英文原样。
- `omit: true` = **这段在中文里不存在**,渲染时什么都不画。

没有 `omit` 的话只有两个选择:把那段留成英文("Long live the 陨落之星万岁!!!!"),
或者把整行压成一种颜色、丢掉服务器给名字加的高亮。两个都更糟。

### 颜色分段的渲染顺序 `order`

`omit` 只能把一段的意思**往后**挪(挪进它后面那一段),挪不到前面。碰上语序整个反过来的句子就不够用了:

```
§aYou received §2750 ᠅ Mithril Powder §afrom killing a §6§lGolden Goblin§a!
```

中文是「你通过击杀**黄金哥布林**获得了 **750 ᠅ 秘银粉末**!」——两段高亮**互换了位置**,
而且各自要带着自己的颜色和占位符一起走。这种情况给每一段写一个 `order`,值是**这一段在中文里排第几**
(从 0 开始):

```json
"segments": [
  { "color": "§a", "text": "You received ",           "zh": "你通过击杀",       "order": 0 },
  { "color": "§2", "text": "%1$s ᠅ Mithril Powder ",  "zh": "%1$s ᠅ 秘银粉末",  "order": 3 },
  { "color": "§a", "text": "from killing a ",         "zh": "获得了 ",          "order": 2 },
  { "color": "§6", "text": "%2$s",                    "zh": "%2$s",             "order": 1 },
  { "color": "§a", "text": "!",                       "zh": "!",               "order": 4 }
]
```

规则:

- **`segments` 本身永远按原文顺序写**。匹配是按原文顺序编译的,顺序写乱了就匹配不上了;
  `order` 只影响画出来的先后。
- **要写就每一段都写**,而且必须是 `0..n-1` 的一个完整排列。只给一部分段写 `order`,
  剩下那些落在哪一位是碰运气;写重了会有一段永远画不出来——屏幕上少半句话,而记录看着一点问题没有。
  `checkTranslations` 会拦这两种。
- 中文语序和英文一致时(绝大多数记录)**不要写** `order`,徒增噪音。
- 写完拿 `./gradlew probe` 或 `replayCapture` 把整行画出来看一眼——每一段单看都对、
  连起来读不通,是这类记录唯一的失败方式。

### GUI_Item 的 lore 数组专用规则

物品 Lore 在游戏里是一个**有序字符串数组**,空行(`""`)本身是有意义的排版,
不能删掉或当噪音过滤。采集 `lore` 数组时:

- 空行也算一条记录,`text` 为空字符串,`translate: false`,`id` 用
  `<item>_blank_<序号>` 命名,保证数组顺序和游戏内一模一样。
- 类似 "Fuel Tank: Not Installed" 这种"当前状态是插槽为空,装了配件后文字会变"的行,
  按占位符处理(`%s` = 当前状态或已安装配件名),不要当成固定文本。
- 遇到"这是不是专有名词(NPC称呼/头衔),要不要翻译"判断不了的词(例如物品 Lore 里提到
  的服务型 NPC 头衔),先按 `translate: true` 采集并在 `gloss` 里写清楚"未确定是否为
  专有名词,需核实",不要自己拍板决定不翻译——避免真正该翻译的内容被漏掉。

## 4. 占位符(可变文本)规范 —— 对应用户想法 2

**结论:仍然用 JSON,不需要另外的 Java 文件。** 用 Java 的
`String.format` 风格占位符 `%s` / `%1$s` / `%2$d` 直接写在 `text` 里,
再用同一条记录里的 `placeholders` 数组描述每个占位符的语义、类型和示例值。

原因:
1. Minecraft/Fabric/NeoForge 的 `Component.translatable` 本身就支持
   `%s` 风格的参数,Opus 写代码时可以直接对应,不需要再设计一套新语法。
2. 只有一个占位符时用 `%s` 即可;同一句话里出现多个占位符、且翻译成中文后
   词序可能调换时,必须用带位置编号的 `%1$s`、`%2$s`,这样中文语序调整时
   参数顺序不会错位(例如英文 "Send %1$s to %2$s" 中文可能要写成
   "把 %1$s 发给 %2$s" 或反过来,位置编号保证替换正确)。
3. **禁止**为了"更完整"而把每个具体值都各写一条记录
   (如 "Collect Diamond items!"、"Collect Gold items!" 各存一条)——
   这是用户想法 2 里明确要避免的臃肿。只存一条带占位符的模板,
   在 `placeholders[].example` 里给 1~2 个例子帮助译者判断语境即可。

`placeholders` 数组每一项字段:

| 字段 | 说明 |
|---|---|
| `token` | 占位符本身,如 `%s`、`%1$s` |
| `desc` | 中文说明这个位置代表什么 |
| `type` | 语义类型,建议用固定词汇:`number` `item_name` `player_name` `npc_name` `percentage` `coins` `location_name` `time` `rarity` `raw` |
| `example` | 示例值(字符串) |

对于 `type: item_name` 等"这个占位符本身就是一个不翻译的专有名词"的情况,
不需要再单独处理——翻译代码在替换时插入的就是那个专有名词本身,天然不翻译。

### 模板必须有自己的词(引擎会拒绝纯占位符模板)

一条记录的 `text` 去掉占位符之后,**必须至少还剩一个字母**,否则引擎直接跳过这条记录
并在启动日志里告警。典型的反例是 `"%s: %s"`:它看上去只是"标签: 数值"的通用写法,
实际上会匹配该渲染面上**每一行**带冒号的文本——计分板侧栏的 `Fossil Dust: %s`、
`Zone: %s`、`Pool: %s` 全部会被它顶掉,而且日志里什么都不会说,表现就是"翻译文件里
明明填好了,游戏里还是英文"。

需要按标签分别翻译时,把具体词句写进模板(`"Lapis Corpse: %s"`、`"Mithril: %s"`),
一个标签一条记录。**这不违反第 4 节禁止的"值枚举"**:那条禁止的是把同一个标签的每个
*取值*各存一条(Collect Diamond / Collect Gold ...),这里拆的是*标签本身*,标签是有限的、
而且每个都要有自己的译名。

同一行有多条记录能匹配时(如 `"Remaining: %s"` 和 `"Remaining: %s goblin(s)"`),
引擎选**模板里字面文本最多**的那条,不用担心文件顺序。

### 同一渲染面上不要写两条模板一模一样的记录

上面那条规则在两条记录**模板完全相同**时就用不上了:字面文本一样多,谁赢取决于文件名谁排前面,
改个文件名答案就变了,输的那条永远画不出来。两条译文一致时这只是白写一份,不一致时就是 bug——
而且最常见的不一致是**颜色**:`"- %s Glacite Powder"` 在委托板文件里记成了一整行、
在山之心文件里带 `segments`,前者文件名排前面,于是山之心的返还清单里"极冰粉末"被刷成了
项目符号的深灰色,旁边同一份清单里的"秘银粉末"却是对的。

两条记录各自都合法、都填了译文,`checkTranslations` 的"每条记录都能应答自己"也照样通过
(它接受同模板的另一条来应答)。所以专门有一条检查拦这个:**同一渲染面上模板相同、分段却不同的
记录会让构建失败**。

正确做法就是 §5.6 那一条:句子写一份放进 `_shared/`,其余各处用 `ref` 引用。
两个 NPC 说同一句话也一样——引擎剥掉 `[NPC] 名字:` 前缀之后就分不出是谁说的了,
留两条不同的译文只会有一条生效。

### 占位符捕获的值:`_shared/Terms.json`

运行时占位符捕到的是服务器塞进来的一整段原文(`Royal Mines`、`Topaz Crystal`、`Glacite`)。
以前引擎只能**整段原样保留**,屏幕上就出现了 "Royal Mines钛"——半个名字一种语言,而且中间没空格。

现在有两层机制处理它,译者基本不用管:

1. **`_shared/Terms.json`** 是一张"占位符值 → 中文"的表。引擎在渲染时对捕获值做**整值精确匹配**,
   查到就换成中文,查不到就保持英文。只对 `placeholders[].type` 在该文件 `applies_to_types`
   里的位置生效(目前是 `location_name` / `mob_name` / `raw`),**故意不含 `item_name` /
   `npc_name` / `player_name`**——那三种正是需求里要求保留英文的位置。
2. **中英之间的空格由引擎自动补**(`TranslationEntry.Seam`)。译文片段和捕获值的接缝处,
   一边是拉丁字母、另一边是汉字时插入一个空格,所以 `%s宝石收集员` 配上 `Amber` 渲染成
   "Amber 宝石收集员"。数字不触发这条规则,`"剩余: %s只哥布林"` 依然是"剩余: 3只哥布林"。

**译者要做的**:照常写 `"%s收集员"` 这样的模板,不要为了空格去改译文;发现某个地名/材料名
应该有中文却还显示英文时,往 `Terms.json` 的 `terms` 数组里加一条,不要把模板拆成值枚举。

**注意**:写死在 `zh` 字符串里的英文(不是占位符),引擎不会去动它——"Jade 水晶"里的那个空格
必须译者自己写。

### 单复数不用各写一条

Hypixel 让名词跟着数量走:`Bits: 53,998` 但 `Bit: 1`,`+3,598 items` 但 `+1 item`。
这是两个不同的字符串,只写一种的话,数量正好是 1 的那一次就不翻译了——而且等你回头看的时候
它已经变回复数了,这种 bug 基本没人报得上来。

中文没有单复数,两种写法译文完全一样,所以**引擎自己处理**:带占位符的记录在编译时,
字面文本里凡是复数样子的词(≥3 个字母、以单个 `s` 结尾、不是 `is`/`bonus`/`Boss` 这类),
末尾那个 `s` 都会变成可选(见 `text/TranslationEntry.eitherNumber`)。

**所以模板里一律写复数那一种,不要写单数。** 折算只有一个方向:`+%s slots` 同时管
`+1 slot` 和 `+2 slots`,而 `+%s slot` 只管 `+1 slot`——数量一超过 1 就掉回英文。
2026-08-31 的实测里 `Each tier: +2 slots`(饰品袋、收纳袋中袋每级加 2 格)就是这么漏的:
记录的 id 写着 `upgrades_each_tier_slots`,`text` 却是单数。同一批还查出 `Adding: +%s slot`、
`%s day` 两条。**不要为单复数写第二条记录**,写复数那一条就够了。

例外是**没有占位符**的记录:它们按原文精确查哈希表,到不了正则那一步。
真遇到"一件固定句子有单复数两种写法"的情况,那两条得各写一条。

### 占位符能捕到什么是受限的

`%s` 编译出来的不是"任意内容",而是按 `placeholders[].type` 决定的一类值(见 `text/Capture.java`):

| `type` | 能捕到的东西 |
|---|---|
| `number` / `percentage` / `coins` / `time` | 数字,可带正负号、千分位、`%`、`k` 之类的后缀 |
| `item_name` / `npc_name` / `location_name` / `mob_name` / `rarity` / `category_name` | 名字:最多 5 个词,两端必须是大写字母或数字开头,不含句末标点 |
| `player_name` | 最多 16 个字母数字下划线 |
| `tier` | 罗马数字(`XII`、`V`),附魔等级 / 小人等级 / 增益等级都是这个形状 |
| `ordinal` | 英文序数(`27th`、`1st`、`88th`)。**渲染时后面那两个字母会被去掉**,因为中文的"第 N 届"把序数写在数字外面,`th` 留着就是句子中间夹两个英文字母。一条模板管四种后缀,不用像日期那样 st/nd/rd/th 各写一条 |
| `raw` / 没写 / 不认识的值 | 最多 8 个词,不含句末标点 |

为什么要限:Hypixel 会把一句长 Lore 折成两行,委托名模板 `"%s Mithril"` 曾经完美匹配上
`"Slay 1 Boss Corleone in the Mithril"` 这半句话(`%s` 捕到了 "Slay 1 Boss Corleone in the"),
于是一句讲打 Boss 的话被画成了 "Slay 1 Boss Corleone in the秘银",下一行还留着英文 "Deposits."。
**所以 `placeholders[].type` 不是给译者看的注释,它会直接影响匹配。** 采集时如果拿不准,
`raw` 是最宽松的默认值,但也仍然拒绝整句话。

**菜单分类名用 `category_name`，不要用 `raw`。** 这类记录的模板是"一个词 + 一个占位符"
(`"Your %s"`、`"%s Settings"`、`"%s Pet"`、`"%1$s Unlocked: %2$s%"`),而 `raw` 允许最多 8 个词的
任意短语——2026-08-27 的实测里 `"Your %s"` 因此把 GUI 上任何以 Your 开头的 Lore 整句都吃了下来
(`"Your withers will travel to and"`、`"Your first daily commission on each"` 等),而它的译文是
裸 `"%s"`,于是 Your 被删掉、剩下半句英文原样画在屏幕上——**不是没翻译,是把原文改坏了**。
`category_name` 走和名字一样的形状规则(最多 5 个词、两端大写开头),半句话进不来,而
Bags / Skills / Other Crystals 这些真正的入口名照旧通过。词表对 `category_name` 生效,
所以这些分类名该翻的照样翻。

**两个 `raw` 挨在一起要小心。** 占位符是"能少吃就少吃"的,所以 `"%1$sx %2$s %3$s [ACTIVE]"`
碰上 `19x Hard Stone XII [ACTIVE]` 会在第一个空格处切开:`%2$s` 捕到 `Hard`、`%3$s` 捕到
`Stone XII`。这不是"没翻译",是**翻乱了**。办法是把其中一半说清楚——上面这一行的后一半是
罗马数字,写成 `type: tier` 之后前一半才知道该停在哪。

### Tab 列表的一行是「标签 + 数值」,两半各查一次表

`Corpse Looter: DONE` 里有两个要翻译的东西:标签是委托任务名,数值是它的进度。引擎在这一面
(`Surface.TABLIST`)先照常按记录查整行、再查标签;**剩下的那半边会去查 `_shared/Terms.json`**,
标签在没有记录应答时也一样。所以:

- **委托名、区域名、材料名这类已经在词表里的标签,不需要再写一条 TabList 记录**——那等于把词表
  抄第二份,Hypixel 新加一个区域就会漏掉一处。`Rampart's Quarry Mithril: DONE` 现在直接渲染成
  「壁垒采石场 - 秘银: 已完成」,两半都来自词表。
- **`DONE` / `✔ Found` / `NOT LOOTED` / `MAX` 这类状态词是"值"**,往词表里加,不要写成记录。
- 数字、进度条、时间(`0%`、`|||||`、`4h`)里没有词,不用管。
- 需要整行连在一起才通顺的行(`%1$s) %2$s %3$s Gemstone`)照常写记录,记录永远优先。

### 行首的项目符号会被剥掉再查一次

菜单里被选中的那一格画成 `▶ Power Crystal`,空岛菜单的加成项前面是 `■`,指南的小节前面是 `⚑`。
这些符号说的是「这一行在列表里的位置」,后面的文字就是语料里已经有的那句话,所以引擎会**多试一次
剥掉符号之后的范围**(见 `text/LineShape.java` 的 `BULLETS`)。写记录时**不要**把符号抄进 `text`,
除非那一行的记录本来就该连符号一起管(整行匹配永远优先)。

注意这张符号表是**列举**出来的,不是按 Unicode 类别判断的:`⸕`、`❤` 这些属性图标也在行首出现,
它们是句子的一部分,译文要原样保留。遇到新的项目符号往那张表里加一个字符即可。

### 「某人的某地」这类名字

侧边栏在博物馆里写的是 `inkkni's Museum`,在别人的私人岛上写的是 `<玩家名>'s Island`。
主人是玩家名,每个人都不一样,**任何表都不可能列全**。引擎的做法是拆开所有格:
词表里只写通名(`Museum → 博物馆`),渲染成「inkkni 的博物馆」;`assets/skyzh/capture/areas.json`
同理,只写 `Museum`/`Island`(见 `text/Possessive.java`)。

只有在**直接查表查不到**时才会拆,所以 `Rampart's Quarry`、`Goblin Queen's Den` 这种表里写全了的
名字仍然按整条词条走,不会变成「Rampart 的采石场」。

### 行首行尾的结构不要写进 `text`

游戏里的一行常常是"结构 + 句子":NPC 台词实际发出来是 `[NPC] Bubu: <台词>`,
Tab 列表的行是 `<标签>: <数值>`。这些结构由代码(`text/LineShape.java`)按渲染面剥离后
再查表,查完原样贴回去并保留原有颜色。所以:

- `text` 里**只写句子本身**,不要写 `[NPC] Bubu: ` 前缀,也不要为了"能匹配上"去补它。
- Tab 列表的标签,写 `"Commissions:"`(带冒号)或 `"Mining Speed"`(不带)都能匹配,
  代码两种形式都会试。

## 5. 一词多义 / 语境相关词的处理 —— 对应用户想法 3

分三层处理,层层兜底:

1. **文件夹隔离**:同一个英文词在 Mining 和 Dungeons 下的用法通常已经因为
   分类不同而天然分开采集,大部分歧义在这一层就被结构解决了,不需要额外操作。
2. **单条记录的 `gloss` 字段**:遇到局部歧义(同一玩法分类下,同一个词在
   不同句子里含义不同),在该条记录写清楚。例如 "Bank" 在 Economy 下可能
   出现在"银行"场景,也可能出现在玩家自己的"个人金库"场景,含义不同就分别加 `gloss`。
3. **全局术语表 `GLOSSARY.md`**:当一个词/短语在**多个文件、多个分类**里
   反复出现且译名必须保持全项目统一(比如 "Fortune" 应统一译"财富"还是
   "幸运"取决于是 Mining Fortune 还是别的语境),记录到 `GLOSSARY.md`,
   翻译阶段作为强制参考,避免同一个词在不同文件里译得不一致。

采集阶段(本阶段)只需要做:发现歧义就随手写 `gloss`,发现是全局性术语就
顺手记一条到 `GLOSSARY.md`。不需要现在就给出中文译名。

## 5.5 已决定的全项目原则

- **天赋名/技能名/限时活动名一律翻译**,不当专有名词处理(区别于 NPC 人名/
  物品自造专名)。例如山之心(Heart of the Mountain)科技树里的天赋名、Mining Fiesta
  之类限时活动名,采集时 `translate` 都设 `true`。详见 `GLOSSARY.md` "山之心天赋名"条目,
  已确定的具体译名(如 Heart of the Mountain → 山峦之心/山心)直接写在该条目里,
  其他玩法分类遇到同类命名(技能树、限时活动、Buff 名等)直接套用这条原则,不用重新讨论。
- **地名也一律翻译**,不当专有名词处理。例如 Glacite Mineshaft → 极冰矿井、
  Glacite Tunnels → 极冰隧道、Dwarven Village → 矮人村庄。只有 NPC 人名和物品
  自造专名(如 "Aspect of the End" 这类武器自创名)才按 §6 的规则保留英文
  不翻译。之前版本把地名归进"不翻译"一类是错误的,已更正。

## 5.6 共享片段库 `_shared/`

物品 Lore 里有大量跨物品重复的通用行(稀有度词 COMMON/RARE/EPIC/...、
"This item can be reforged!"、"* Soulbound *"、"Accessory Power: +N" 等)。
这些已经统一抽到 `original_text/_shared/` 目录下的共享文件里(`Rarity.json`、
`Item_Boilerplate.json`),**采集新物品时遇到这类通用行,不要重复整段抄进物品自己的
文件里**,改成一条引用记录:

```json
{
  "id": "some_item_reforge_hint",
  "ref": "_shared/Item_Boilerplate.json#reforge_hint",
  "context": "该物品 Lore 末尾的通用重铸提示行"
}
```

`ref` 格式为 `<相对 original_text/ 的路径>#<被引用条目的 id>`。如果遇到共享库里没有
覆盖的新通用行,先添加到共享文件里再引用,不要在物品文件里另起一份。

## 6. 不翻译的内容如何采集

NPC 人名、物品的自造专有名称(如 "Aspect of the End" 这类武器自创名。
注意 "Mithril" 本身作为矿物材料名**要翻译**成"秘银",不属于这条)——
**依然要采集**,只是 `translate` 设为 `false`。
原因:翻译系统/资源包最终要生成完整的语言文件,如果这些专有名词完全不出现
在数据里,Opus 写代码时无法区分"这个位置故意留空/留英文"和"这个位置忘了采集"。
地名不在这条例外范围内,一律翻译,见 5.5。

## 6.5 运行时采集的输出怎么搬进来

Mod 里有一个默认关闭的开发者开关 `captureUntranslated`(见 `SOURCES.md` 的「运行时采集」一节),
打开之后会把游戏里**语料答不上来的服务器原文**写到 `skyzh-capture/` 下,分三堆:

- `untranslated/` —— 没有任何记录应答的行,要新写记录。
- `mixed/` —— 有记录应答了,但屏幕上仍然中英混杂。这一堆**不用新写记录**,
  `_capture.matched_record` / `matched_file` 已经指出是哪个文件的哪条,
  按 `_capture.fix` 里的提示补 `segments[].zh` 或往 `_shared/Terms.json` 加词条即可。
- `colour/` —— 有记录应答了、每个字都译成了中文,**颜色被压平了**:游戏里这一行中途换色,
  语料里却记成了一整行,于是整段译文被刷成最前面那个颜色(金色的 5 旁边一个白色的 `(+`)。
  这一堆同样不用新写记录,而且它比另外两堆更值钱——启动日志只说得出"哪条记录压平了颜色",
  说不出**颜色是在哪儿换的**;采集文件里那个 `segments` 数组就是按服务器实际发的边界切好的,
  直接抄进 `_capture.matched_record` 指的那条记录,再把原来的整句译文按段拆进各自的 `zh`。

两堆里都按本文件的结构分目录(玩法 / 渲染面 / 名字),**记录格式就是本文件第 3 节规定的那个**,
颜色码已经填进 `raw`、变色的行已经切好 `segments`、`zh` 留空。搬进 `original_text/` 只要四步:

1. **删掉整个 `_capture` 块。** 那是采集器的自述,不是语料的一部分。
2. **核对 `placeholders`。** 采集器只有在同一位置见过 ≥2 种取值时才敢标成占位符,
   见过的取值全列在 `_capture.observed` 里;`type` 只会是 `number` 或 `raw`
   (最宽松的那个),**该收紧成 `item_name` / `location_name` 之类的要人工改**——
   `type` 会直接影响匹配范围,见第 4 节末尾。
3. **补 `context` 和 `gloss`。** 采集器不知道这句话什么时候出现、谁说的。
4. **填 `zh`。** 没填的记录不会影响游戏内显示,可以分批做。

采集文件里还有几个字段是给排错用的,搬运时一并删掉:

- `_capture.seen_in` —— 采到这一行时侧边栏报的**地点**(`Your Island`、`Dwarven Mines`)。
  和文件所在的玩法目录不是一回事:私人岛屿、大厅、博物馆的通用文本都落进 `Hub_General`,
  光看目录名会以为都是在大厅采的。

- `_capture.raw_escaped` —— 这一行含有肉眼看不见的字符(私用区图标、不间断空格)时才出现,
  把它们写成 `\uXXXX`。
- `_capture.near_miss` —— **语料里其实已经有这句话,只差在不可见字符上**。
  这是本项目最难发现的一类问题(屏幕、日志、数据文件三边都看不出异常),
  遇到它不是要新增记录,而是要去改它指出的那条已有记录。

**补完记录之后把采集结果倒回去看一眼**:

```bash
./gradlew replayCapture -Pcapture=logs/skyzh-capture/untranslated/Mining/ChatMessage
```

采集文件里逐字留着原文(连颜色码和图标字形都在),这个任务把它们重新过一遍引擎,
逐行打印「现在渲染成什么样」。`checkTranslations` 只知道语料对自己的说法,
分段写反了、空格夹在两个汉字中间、某个值忘了加进 `Terms.json`——这些都能通过它,
屏幕上却还是不对;在这里是一行输出的事。

## 7. 文件命名

- NPC_Message 文件名 = NPC 英文名,和 `npc` 字段一致,如 `King.json`。
- 同名 NPC 分属不同版本/轮换角色(如 King 轮换 7 个名字)算**同一个文件**,
  轮换的具体名字放在 `placeholders`/`example` 或顶层 `aliases` 字段里,
  不要拆成 7 个文件。
- GUI_Title / GUI_Item 文件名 = 菜单名或物品/物品组名的英文,空格转下划线。
